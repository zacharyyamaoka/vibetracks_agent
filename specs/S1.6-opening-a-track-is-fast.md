# S1.6 Opening a track shows its page fast

## Requirement

> Please add a KPi which is how fast the screens apper when you click them right now they take wayyyyy to long to load: Please add this an an objective you track. make like a repeatable determinstic way to measure it, and then start making some improvements so that this loads faster

Zach, 2026-11-25, with a screenshot of his Preview: "Blackbox Agent Agent" selected and the main pane blank white
while it loaded. Quoted exactly ([feedback note](../feedback/2026-11-25-screens-load-too-slowly.md)).
[OBJECTIVES.md](../OBJECTIVES.md) lists every item; this note explains it and never overrides it.

## What it means

Click a track and its box's own page is on screen almost at once, every time: the first click on a box and every
click after, a box that commits its site and a box whose site the package builds, a box that just got a new commit.
Not a blank pane, not a "building" page, not the previous box's page.

**The KPI, `open_ms`:** the median, over a fixed click sequence, of the time from the `pointerdown` on a track's
sidebar row to the first animation frame in which that box's own content is visible in the main pane, taken over the
**package boxes'** opens: every box of Zach's is a package box since blackbox-agent 0.1 (its site built by the
package, the dashboard viewer loaded), so that is the number that moves when his boxes open faster. The fixture's
files boxes (the older layout, a committed one-file site) and its box with no site are opened in the same sequence and
held by the second bound below.

- **t0** is the row's `pointerdown`, stamped in the page (`performance.timeOrigin + event.timeStamp`).
- **t1** is the first animation frame in which the box's content marker is visible inside the main pane: an element
  holding the marker text has a box inside its frame's viewport, is not hidden (display, visibility, opacity up its
  chain), is topmost at its centre, in a frame that is itself shown and topmost there, at every level up to the top
  page, right of the sidebar. Stamped in the frame that shows it (`performance.timeOrigin + the rAF timestamp`), by
  a script that runs in every frame, cross-origin frames included; never by polling from outside the page.
- The marker is the box's own: a files box's site marker, a package box's objective name (its built landing and
  dashboard both print it), a box with no site its README line. A README shown for a box that has a site, a
  "building" page or another box's page never carries it.
- **The click sequence** ([`ruler/suite/groups/speed.mjs`](../ruler/suite/groups/speed.mjs)): the dev fixture's boxes, plus six package boxes
  (built by the version itself, as Zach's boxes are) and the extra box, added with `vt add`; a fresh `vt serve` and
  a fresh browser; the page ready, then 10 s of nothing; round 1 opens every box once (cold), in an order fixed by the
  seed; a commit lands in two boxes; three more rounds open every box again (warm). Each open is a real click: the
  pointer rests on the row 150 ms, presses 80 ms, releases; 1 s separates two opens. An open whose page is not on
  screen within 10 s counts as 10 s.

## Why

He clicks a track to see that box's work; a pane that stays blank for a second or more breaks the flow every time.
The thresholds are defaults he can overrule ([OBJECTIVES.md](../OBJECTIVES.md) §10.7): **`open_ms` ≤ 400 ms** and **nineteen opens in
twenty, of any box, ≤ 1000 ms** (the p95; "the slowest" read so that one stall on a shared machine cannot flip it).
Basis: Jakob Nielsen's response-time limits (*Usability Engineering*, 1993, §5.5, after Miller 1968: 0.1 s feels
instantaneous, 1 s keeps the user's flow of thought uninterrupted, 10 s holds attention) and the Doherty threshold
(Doherty and Thadani, *The Economic Value of Rapid Response Time*, IBM, 1982: productivity climbs steeply once the
system answers in under about 400 ms). The
target the KPI is driven toward is 100 ms, Nielsen's "instantaneous".

## How it is checked

`S1.6 *`, two checks, each judged on each dev run by itself: the run's package-box median within 400 ms, and the
p95 of the run's opens of every box within 1000 ms. The `deterministic` gate holds them like every other check: both
runs must agree. Reported with them, never selected on: each kind's median, a package box's first and later opens,
the slowest open, and per open the requests and bytes the browser fetched between the press and the page showing and
the builds the version finished in that time.
